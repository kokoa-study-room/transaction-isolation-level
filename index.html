개요

격리수준이란 무엇인가?

데이터 정합성과 동시 처리 성능 사이의 균형을 결정하는 핵심 개념.

트랜잭션 격리수준(Transaction Isolation Level)이란, 동시에 여러 트랜잭션이 실행될 때 한 트랜잭션이 다른 트랜잭션의 연산에 영향을 받지 않도록 하는 정도를 말합니다.

낮은 격리 수준은 동시 처리 능력(Concurrency)을 높이지만, Dirty Read, Non-Repeatable Read, Phantom Read 같은 데이터 일관성 문제가 발생할 수 있습니다.

높은 격리 수준은 데이터 일관성을 보장하지만, 트랜잭션 간 잠금(Lock)으로 인해 동시 처리 능력이 저하됩니다.

즉, 데이터 정합성과 성능은 반비례 관계입니다. 각 시스템의 요구사항에 따라 적절한 격리 수준을 선택해야 합니다.

정합성 낮음 → 성능 높음
정합성 높음 → 성능 낮음

4가지 격리수준

격리수준 상세 설명

낮은 단계부터 높은 단계까지, 각 격리수준이 허용하는 범위와 발생 가능한 문제를 알아봅니다.

👁️
Isolation Level 1

READ UNCOMMITTED

커밋이 되지 않은 트랜잭션의 데이터 변경 내용을 다른 트랜잭션이 읽는 것을 허용합니다. 가장 낮은 격리 수준으로, 높은 동시성을 제공하지만 데이터 일관성이 가장 취약합니다. 아직 완료되지 않은 변경사항을 읽을 수 있어 롤백 시 문제가 생깁니다.

Dirty Read 발생 Non-Repeatable Read 발생 Phantom Read 발생
✅
Isolation Level 2

READ COMMITTED

커밋이 완료된 트랜잭션의 변경사항만 다른 트랜잭션에서 조회할 수 있습니다. 특정 트랜잭션이 진행되는 동안 다른 트랜잭션은 해당 데이터에 접근할 수 없습니다. PostgreSQL, Oracle, SQL Server의 기본값이며 가장 널리 사용되는 수준입니다.

Dirty Read 미발생 Non-Repeatable Read 발생 Phantom Read 발생
🔄
Isolation Level 3

REPEATABLE READ

한 트랜잭션에서 특정 레코드를 조회할 때 항상 같은 데이터를 응답하도록 보장합니다. 기존 행의 수정은 방지하지만, 새로운 행의 삽입은 막지 않습니다. MySQL InnoDB의 기본 격리 수준이며, MVCC로 구현됩니다.

Dirty Read 미발생 Non-Repeatable Read 미발생 Phantom Read 발생
🔒
Isolation Level 4

SERIALIZABLE

특정 트랜잭션이 사용 중인 테이블의 모든 행을 다른 트랜잭션이 접근할 수 없도록 잠급니다. 가장 높은 데이터 정합성을 보장하지만 성능이 가장 낮습니다. MySQL에서는 단순한 SELECT 쿼리도 공유 잠금(Shared Lock)을 획득합니다.

SQL 코드 예제

격리수준별 실제 SQL 시나리오

격리수준을 선택하고 단계별로 두 트랜잭션이 어떻게 동작하는지 직접 확인해보세요.

Dirty Read 시나리오
미커밋 데이터를 읽다가 롤백 발생

트랜잭션 A가 커밋하지 않은 변경 내용을 트랜잭션 B가 읽습니다. 이후 A가 롤백하면 B가 읽은 데이터는 실제로 존재하지 않는 유령 데이터가 됩니다.

-- 초기 데이터 CREATE TABLE accounts ( id INT, balance INT ); INSERT INTO accounts VALUES (1, 500);
트랜잭션 A
SET TRANSACTION ISOLATION LEVEL READ UNCOMMITTED; BEGIN; UPDATE accounts SET balance = 1000 WHERE id = 1; -- ⚠ 아직 COMMIT 전! ROLLBACK; -- balance 다시 500으로 복원
트랜잭션 B
SET TRANSACTION ISOLATION LEVEL READ UNCOMMITTED; BEGIN; SELECT balance FROM accounts WHERE id = 1; -- 결과: 1000 ← 미커밋 데이터! -- 💥 Dirty Read! -- 읽은 1000은 이제 없는 값 COMMIT;
1 / 5
두 트랜잭션이 READ UNCOMMITTED 격리수준으로 시작합니다.
트랜잭션 A가 balance를 500 → 1000으로 UPDATE합니다. 아직 커밋하지 않았습니다.
트랜잭션 B가 balance를 SELECT합니다. 커밋되지 않은 값 1000을 읽어버립니다! (Dirty Read)
트랜잭션 A가 ROLLBACK합니다. balance는 원래 500으로 되돌아갑니다.
B가 읽은 1000은 이제 존재하지 않는 유령 데이터입니다. 💥 Dirty Read 발생!
Non-Repeatable Read 시나리오
같은 행을 두 번 읽었는데 값이 바뀜

Dirty Read는 방지하지만, 트랜잭션 A가 진행 중에 B가 커밋을 완료하면 A가 같은 쿼리를 다시 실행했을 때 다른 결과를 얻습니다.

-- 초기 데이터 CREATE TABLE accounts ( id INT, balance INT ); INSERT INTO accounts VALUES (1, 500);
트랜잭션 A
SET TRANSACTION ISOLATION LEVEL READ COMMITTED; BEGIN; SELECT balance FROM accounts WHERE id = 1; -- 결과: 500 ✓ SELECT balance FROM accounts WHERE id = 1; -- 결과: 1000 ← 달라졌다! COMMIT; -- 💥 Non-Repeatable Read!
트랜잭션 B
-- (별도 세션에서 진행) BEGIN; UPDATE accounts SET balance = 1000 WHERE id = 1; COMMIT; -- A의 2번째 SELECT 전에 커밋 완료
1 / 5
트랜잭션 A가 READ COMMITTED 격리수준으로 시작합니다. Dirty Read는 방지됩니다.
트랜잭션 A가 balance를 처음 읽습니다. 결과: 500 ✓
트랜잭션 B가 balance를 1000으로 변경하고 COMMIT합니다.
트랜잭션 A가 같은 쿼리를 다시 실행합니다. B가 커밋했으므로 결과: 1000! 값이 바뀌었습니다.
같은 쿼리를 두 번 실행했는데 다른 결과! 💥 Non-Repeatable Read 발생!
Phantom Read 시나리오
같은 범위 쿼리인데 새 행이 나타남

REPEATABLE READ는 기존 행의 변경은 방지하지만 새 행의 삽입까지는 막지 않습니다. 범위 조건 쿼리를 두 번 실행하면 결과 행 수가 달라질 수 있습니다.

-- 초기 데이터 CREATE TABLE orders ( id INT, amount INT ); -- amount > 100인 행: 3개 INSERT INTO orders VALUES (1,150),(2,200),(3,300);
트랜잭션 A
SET TRANSACTION ISOLATION LEVEL REPEATABLE READ; BEGIN; SELECT COUNT(*) FROM orders WHERE amount > 100; -- 결과: 3 ✓ SELECT COUNT(*) FROM orders WHERE amount > 100; -- 결과: 4 ← 새 행이 나타남! COMMIT; -- 💥 Phantom Read!
트랜잭션 B
-- (별도 세션에서 진행) BEGIN; INSERT INTO orders (id, amount) VALUES (4, 200); COMMIT; -- A의 2번째 SELECT 전에 삽입!
1 / 5
트랜잭션 A가 REPEATABLE READ 격리수준으로 시작합니다. 기존 행 변경은 방지됩니다.
amount > 100인 주문 수를 셉니다. 결과: 3 ✓
트랜잭션 B가 amount=200인 새 행(id=4)을 삽입하고 COMMIT합니다. 새 행 삽입은 막지 않습니다!
트랜잭션 A가 같은 쿼리를 다시 실행합니다. 결과: 4! B가 삽입한 새 행이 보입니다.
같은 WHERE 조건인데 행 수가 달라졌습니다. 💥 Phantom Read 발생!
완전 격리 시나리오
범위 잠금으로 Phantom Read까지 차단

SERIALIZABLE에서 SELECT는 범위 잠금(Range Lock)을 획득합니다. 트랜잭션 B의 INSERT는 A가 COMMIT할 때까지 대기하므로 Phantom Read가 완전히 차단됩니다.

-- 초기 데이터 CREATE TABLE orders ( id INT, amount INT ); -- amount > 100인 행: 3개 INSERT INTO orders VALUES (1,150),(2,200),(3,300);
트랜잭션 A
SET TRANSACTION ISOLATION LEVEL SERIALIZABLE; BEGIN; SELECT COUNT(*) FROM orders WHERE amount > 100; -- 결과: 3 (범위 잠금 획득 🔒) SELECT COUNT(*) FROM orders WHERE amount > 100; -- 결과: 3 ✅ 변함없음! COMMIT; -- 잠금 해제 → B 실행됨
트랜잭션 B
-- (별도 세션에서 진행) BEGIN; INSERT INTO orders (id, amount) VALUES (4, 200); -- ⏳ A의 잠금 해제 대기 중... -- A COMMIT 후 INSERT 실행됨 COMMIT;
1 / 5
트랜잭션 A가 SERIALIZABLE 격리수준으로 시작합니다. 가장 강력한 격리를 제공합니다.
SELECT 실행 시 MySQL이 amount>100 범위에 공유 범위 잠금을 획득합니다. 결과: 3
트랜잭션 B가 INSERT를 시도하지만 A의 범위 잠금으로 인해 대기 상태가 됩니다. ⏳
트랜잭션 A가 동일 쿼리를 다시 실행합니다. 결과: 3 (변함없음!) ✅ Phantom Read 없음!
A가 COMMIT하면 잠금이 해제되어 B의 INSERT가 실행됩니다. ✅ 완전한 격리 달성!
동시성 문제

발생 가능한 3가지 문제

격리수준이 낮을수록 다음 3가지 데이터 정합성 문제가 발생할 수 있습니다.

🧹

Dirty Read

한 트랜잭션이 다른 트랜잭션이 변경 중인 (아직 커밋되지 않은) 데이터를 읽는 현상. 나중에 해당 트랜잭션이 롤백되면, 읽었던 데이터는 존재하지 않는 데이터가 됩니다. 데이터 일관성을 근본적으로 파괴합니다.

시나리오
트랜잭션 A
트랜잭션 B
balance = 1000 UPDATE
balance 읽기 → 1000
ROLLBACK ↩
B가 읽은 1000은 유령 데이터!
👻

Phantom Read

한 트랜잭션이 동일한 쿼리를 두 번 실행했을 때, 두 번의 쿼리 사이에 다른 트랜잭션이 삽입·갱신·삭제 작업을 수행하여 결과 집합이 달라지는 현상. 마치 유령처럼 새로운 행이 나타나거나 사라집니다.

시나리오
트랜잭션 A
트랜잭션 B
SELECT COUNT(*) → 5
INSERT 새 행 + COMMIT
SELECT COUNT(*) → 6
동일 쿼리인데 결과가 다름!
🔁

Non-Repeatable Read

같은 트랜잭션 안에서 동일한 행을 두 번 읽었을 때 다른 결과를 얻는 현상. 첫 번째 읽기와 두 번째 읽기 사이에 다른 트랜잭션이 해당 데이터를 수정하고 커밋했기 때문에 발생합니다.

시나리오
트랜잭션 A
트랜잭션 B
name 읽기 → "Alice"
UPDATE name="Bob" COMMIT
name 재읽기 → "Bob"
같은 행인데 값이 바뀜!
비교표

격리수준별 문제 발생 여부

격리수준을 선택하면 해당 행이 강조됩니다.

격리수준 Dirty Read Non-Repeatable Read Phantom Read
READ UNCOMMITTED 발생 발생 발생
READ COMMITTED 미발생 발생 발생
REPEATABLE READ 미발생 미발생 발생
SERIALIZABLE 미발생 미발생 미발생

↑ 행을 클릭하면 해당 격리수준이 강조됩니다. MySQL InnoDB 기본값은 REPEATABLE READ.
